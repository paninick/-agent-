# 验证标准 (Verification Standards)

> **更新日期**：2026-06-30
> **目的**：定义每个环节的质量门禁和验证标准

---

## 一、总体原则

```
门禁原则 (Gate Principle):
  - 每个环节必须通过验证才能进入下一环节
  - 不通过 = 阻塞整个流程
  - 验证失败必须升级，不能"略过"

证据原则 (Evidence Principle):
  - 任何"通过"必须有可复现的证据
  - 任何"不通过"必须有具体原因
  - 验证记录必须可审计 (audit_trail)

可量化原则 (Quantifiable Principle):
  - 阈值必须数字明确，不能"差不多"
  - 测量方法必须可重复
  - 异常值必须可解释
```

## 二、各环节验证门禁

### 2.1 Collector 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| HTTP 状态码 | = 200 | 标记 failed，重试备用源 |
| 响应时间 | < 10 秒 | 重试，仍超时则降级 |
| 响应结构 | 符合预期 schema | 标记 anomaly |
| 必需字段 | 100% 存在 | completeness < 1.0 |
| 字段类型 | 100% 正确 | 标记 type_error |
| 字段值范围 | 在合理区间 | 标记 out_of_range |
| 数据新鲜度 | 满足 TTL | 标记 stale |
| API 配额 | < 80% | 标记 budget_warning |

**门禁**：上述全部通过 → 状态 success；任何失败 → 不进入 Cleaner

### 2.2 Cleaner 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 单位转换 | 因子合理 (±0.1%) | 标记 unit_error |
| 口径对齐 | 与 reference 一致 | 标记 caliber_mismatch |
| 异常值检测 | Z-score < 3 | 标记 outlier |
| 缺失率 | < 20% | 标记 low_quality |
| 实体消歧成功率 | > 95% | 标记 entity_ambiguous |
| 时间格式 | ISO 8601 UTC | 标记 time_format_error |

**门禁**：质量分 >= 0.8 → 进入 Weigher；< 0.8 → 标记为 low_quality，可作为辅助证据

### 2.3 Weigher 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 基础权重 | 在 0-1 区间 | 标记 weight_invalid |
| 时效因子 | 符合衰减规则 | 标记 stale |
| 完整性因子 | 与 quality_score 一致 | 标记 integrity_mismatch |
| 交叉验证 | 至少 1 个 cross_reference | 标记 no_corroboration |
| 反证检查 | 至少 0 个反证（自动） | 不阻挡，但记录 |
| 最终权重 | > 0.3 (辅助) / > 0.6 (主) | < 0.3 丢弃 |

**门禁**：final_weight > 0.6 → conclusion_eligible = true；0.3-0.6 → auxiliary；< 0.3 → 丢弃

### 2.4 Reasoner 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 结论明确性 | 一句话，无歧义 | 重做 |
| 证据数量 | 至少 1 条 S/A+ 证据 | 标记 insufficient_evidence |
| 传导链完整性 | 每步有 evidence | 标记 chain_gap |
| 多路径验证 | 至少 1 条独立路径 | 标记 single_path |
| 反证搜索 | 至少尝试 1 次 | 标记 no_counter_search |
| 置信度校准 | 与历史对比偏差 < 0.2 | 标记 overconfident |
| 数据缺口 | 显式列出 | 缺失则标记 |
| 边界条件 | 显式声明 | 缺失则标记 |
| 反馈环 | 识别（如存在） | 缺失则标记 |

**门禁**：
- 置信度 >= 0.7 + 无盲区 → 可信结论
- 0.5-0.7 → 标注限制条件的结论
- 0.3-0.5 → 标记假设
- < 0.3 → 不输出，标记"数据不足"

### 2.5 Devil's Advocate 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 模型异源 | 与 Reasoner 不同 | 不通过 |
| 逻辑一致性 | 结论能由证据推出 | 标记 logic_gap |
| 证据引用准确 | 声称的 evidence_ids 真的支持 | 标记 weak_evidence |
| 反证盲区 | 至少尝试 3 种反驳路径 | 标记 blind_spot |
| 数值正确 | 推导链数学验证 | 标记 math_error |
| 时效性 | 数据是否过期 | 标记 stale_data |
| 边界条件 | 是否声明 | 标记 missing_boundary |

**输出**：verdict = PASS / WARN / FAIL / ESCALATE

```
PASS: 全部通过
WARN: 有小问题但不致命，建议标注后入库
FAIL: 有严重问题，Reasoner 必须重做
ESCALATE: Verifier 无法判断，升级人工
```

### 2.6 Predictor 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 场景完整性 | 至少 3 个场景 | 标记 insufficient_scenarios |
| 概率和 | = 1.0 (允许 ±0.01) | 标记 probability_mismatch |
| 前提条件 | 显式列出 | 缺失则标记 |
| 失效条件 | 显式列出 | 缺失则标记 |
| 历史类比 | 至少 1 个 | 缺失则标记 unprecedented |
| 时间线 | 30/90/180/360 天分阶段 | 缺失则标记 |

### 2.7 Writer 验证

| 检查项 | 阈值 | 失败处理 |
|---|---|---|
| 等级分类 | L0/L1/L2/L3 正确 | 标记 grade_misclass |
| Obsidian 路径 | 符合命名规范 | 标记 path_invalid |
| frontmatter | 所有必需字段存在 | 标记 missing_metadata |
| Ark 同步 | 数据一致 | 重试 |
| IMA 同步 | 仅 L0/L1 同步 | 阻塞 L2/L3 同步 |
| audit_trail | 完整可追溯 | 标记 incomplete_audit |

## 三、回测验证 (Backtest Validation)

### 3.1 历史预测 vs 实际结果

```
目的：验证系统预测能力，避免"自圆其说"

流程：
1. 选取 3 个月前的真实数据
2. 假装不知道结论，跑完整流程
3. 比较系统输出 vs 实际结果
4. 统计准确率

指标：
  direction_accuracy: 方向正确率（目标 > 80%）
  magnitude_accuracy: 量级误差（目标 < 30%）
  false_positive_rate: 误报率（目标 < 10%）
  false_negative_rate: 漏报率（目标 < 10%）
```

### 3.2 历史场景测试

```
测试场景库:
  - 2022 Q2: 棉花暴涨 20% → 越南工厂真实成本传导?
  - 2023 Q3: 越南 HS61 出口超美 50% → 美国市场份额是否真实?
  - 2024: 棉价低位但越南面料价不降 → 库存缓冲?
  - 2024 Q4: 美国大选影响 → 关税预警准确度?
  
每个场景:
  1. 选取当时数据快照
  2. 系统产出预测
  3. 对比实际发展
  4. 评分
```

## 四、模型能力矫正

### 4.1 标准化测试集

```yaml
calibration_tests:
  # 必须用真实数据测试，不是合成数据
  structured_extraction:
    input: "已知答案的 SEC 10-K 字段"
    expected: "答案"
    scoring: "exact_match 或 tolerance(0.01)"
    examples:
      - "GAP Inc FY2024 营收: $15.1B"
      - "Inditex 2023 营业利润率: 18.5%"
  
  causal_reasoning_short:
    input: "3 步传导 + 已知结论"
    expected: "结论"
    scoring: "direction_and_magnitude"
  
  counter_evidence_search:
    input: "已知反证的场景"
    expected: "能否找到反证"
    scoring: "recall"
  
  hallucination_test:
    input: "模型不可能知道的问题"
    expected: "拒绝/标 unknown"
    scoring: "refusal_rate"
```

## 五、异常检测规则

### 5.1 数据异常

```
价格异常:
  - Z-score > 3 → outlier
  - 同比/环比 > 3σ → spike
  - 24h 内变化 > 5% → 重大事件

数量异常:
  - 进口量为 0 但历史均值 > 0 → 报送缺失
  - 进口量暴增 5 倍 → 转单嫌疑
  - 出口量远低于进口量 → 库存积压

时间异常:
  - 数据时间戳晚于当前 > 90 天 → 数据滞后
  - 同一指标不同源差异 > 20% → 口径差异
```

### 5.2 系统异常

```
Agent 失败率 > 20%:
  → 触发进化机制 Level 1
  → 检查 prompt/模型

连续 3 次 Devil's Advocate FAIL:
  → 触发进化机制 Level 2
  → 检查框架/任务拆分

API 用量超预算:
  → 告警
  → 降级非关键任务

数据缺口堵塞决策:
  → 列出缺口清单
  → 评估缺口影响
  → 优先填补关键缺口
```

## 六、质量指标

### 6.1 内部指标 (每月评估)

```
1. 数据覆盖度 = 已覆盖维度 / 6
   目标: > 80% (每月)

2. 数据新鲜度 = < 30 天的核心指标比例
   目标: > 90%

3. 自动化率 = 无人值守完成的任务 / 总任务
   目标: > 80%

4. 探针成功率 = 成功探针 / 总探针
   目标: > 95%

5. 告警准确率 = 真实告警 / 总告警
   目标: > 70%

6. 平均响应时间 (信号→通知)
   目标: < 5 分钟 (紧急)
```

### 6.2 外部指标 (季度评估)

```
1. 结论准确率 = 准确预测 / 总预测
   测量: 回测历史场景
   目标: > 70%

2. 决策采纳率 = 用户采纳系统结论的比例
   目标: > 50%

3. 用户反馈 NPS
   目标: > 40

4. 错误发现率 = 系统自主发现的数据矛盾 / 全部数据矛盾
   目标: > 30%
```

## 七、升级流程

```
自动处理 (无需人工):
  - 单条数据异常 (自动剔除)
  - 单次 API 失败 (重试)
  - 单个 Agent 失败 (重试或降级)

需要人工确认:
  - Devil's Advocate ESCALATE
  - 连续 3 次同类型失败
  - 关键结论置信度 < 0.3 但决策需要

需要立即升级:
  - 关键数据源永久失效
  - 模型供应商政策变更
  - 法规变化 (如《数据安全法》新规)
  - 系统判断 "前所未有" 事件
```

## 八、安全合规验证

### 8.1 数据脱敏验证

```
定期审计:
  - 检查所有 L1/L2/L3 数据是否在合适位置
  - L2 数据是否在云端被访问 (违规)
  - L3 数据是否被脱敏后发到外部 (违规)
  - API key 是否在日志中泄露 (违规)

合规清单:
  - 个人信息保护法 (中国): 联系人/员工/邮箱必须 L3
  - 数据安全法: 重要数据出境需评估
  - GDPR (欧盟): 涉及欧盟居民数据需特别处理
```

### 8.2 访问控制验证

```
每月审计:
  - 谁访问了什么数据
  - 异常访问模式 (深夜/大量)
  - 凭据轮换时间
  - 已撤销凭据是否被使用
```
