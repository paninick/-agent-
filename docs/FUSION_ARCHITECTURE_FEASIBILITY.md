# 融合架构可行性分析（MCP + Skill + World Model Runtime）

> **版本**：v1.0 | **日期**：2026-07-01
> **目的**：评估 A+B+C 融合系统的可行性、已具备条件、缺口、实现路径
> **前提**：基于 v3 产链引擎已有底盘（9 环节 DAG + 56 信息源 + 14 个已装 Skills + 加工费模型）

---

## 一、融合系统的本质

```
World Runtime = Simulation Engine + Execution Engine + Policy Engine

即：这个世界模型能做三件事——
  1. 执行（A）：用 MCP/Skills 抓数据、调 API、写报告
  2. 仿真（B）：模拟"如果棉花涨 10%，整条链会怎样"
  3. 决策（C）：给出"应该囤料还是观望"的最优建议
```

### 与现有系统的关系

| 现有系统 | 融合系统中的位置 | 差距 |
|---------|----------------|------|
| Obsidian 知识库 | World State 的持久化存储 | ✅ 已有 |
| 因果 DAG（9 环节） | Causal Graph 的骨架 | ✅ 已有（系数待精化） |
| national-stats-mcp | 输入层 MCP（经济数据） | ✅ 已安装 |
| 加工费模型 | Simulation 的参数 | ✅ 已建模（能源/人工分离） |
| 14 个已装 Skills | Execution Engine 的能力库 | ✅ 已安装 |
| v3 7 角色 Agent | Policy Engine 的执行者 | ⚠️ 待配置 |
| 10 个工作流 | 主循环的骨架 | ✅ 已设计 |

## 二、可行性逐层评估

### 2.1 Layer 1：Execution Engine（MCP + Skills）—— ✅ 可行

```
已有条件：
  ✅ national-stats-mcp（国统局 CPI/PPI/GDP/零售额）
  ✅ firecrawl（网页抓取/爬虫/监控）
  ✅ Agent-Reach（Twitter/Reddit/B站/小红书）
  ✅ ECC（67 agents + 277 skills）
  ✅ Superpowers（14 个开发纪律技能）
  ✅ firecrawl monitor（网页变化监控）
  
已有 MCP：
  ✅ 国统局（免费，无需 Key）
  ✅ 通达信（待配置，需注册）
  ✅ 企查查/天眼查（待配置，需 Key）
  ✅ WebSearch + WebFetch（内置）
  
缺口：
  ⚠️ 柯桥指数 MCP（需 Playwright 爬虫）
  ⚠️ 海关总署 MCP（需 Playwright 爬虫）
  ⚠️ 通达信 MCP（需注册账号）
  ⚠️ 企查查/天眼查 MCP（需 API Key）
```

**可行性判定**：**90% 可行**。核心 MCP 已有，缺口可通过 Playwright 爬虫补齐。

### 2.2 Layer 2：Simulation Engine（世界仿真）—— ⚠️ 部分可行

```
已有条件：
  ✅ 因果 DAG（9 条边，系数已验证）
  ✅ 加工费模型（能源/人工分离，PPI 驱动）
  ✅ 传导系数（棉花→纱线 0.72，PTA→POY 0.96）
  ✅ 弹性系数（CPI 衣着 -0.5，待验证）
  ✅ 国统局月度数据（PPI/CPI/零售额）
  
缺口：
  ❌ 蒙特卡洛模拟器（需要编写）
  ❌ 跨域传导模型（棉花→化纤→面料→成衣→零售的全链路模拟）
  ❌ 情景分支引擎（"如果棉花涨 10%"的 what-if 模拟）
  ❌ 不确定性量化（系数的置信区间需要更多数据）
  ❌ 人工行为模拟（品牌定价策略、消费者反应）
```

**可行性判定**：**60% 可行**。因果 DAG + 系数已有，但蒙特卡洛模拟器和情景引擎需要从零编写。这是最大的工作量。

### 2.3 Layer 3：Policy Engine（决策优化）—— ⚠️ 部分可行

```
已有条件：
  ✅ 7 角色 Agent 架构（Collector→Cleaner→Weigher→Reasoner→Devil→Predictor→Writer）
  ✅ Superpowers 决策框架（brainstorming + writing-plans + executing-plans）
  ✅ 因果推理能力（causal_dag + scenario_predict + counter_evidence）
  ✅ Obsidian 写入（决策结果持久化）
  
缺口：
  ❌ 多目标优化器（成本最小 vs 质量最高 vs 交期最短）
  ❌ 风险评分模型（供应链中断概率、汇率风险概率）
  ❌ 约束求解器（产能约束、资金约束、MOQ 约束）
  ❌ 策略库（囤料策略、锁汇策略、客户分级策略）
```

**可行性判定**：**50% 可行**。Agent 架构和推理能力已有，但优化器和约束求解需要额外开发。

## 三、关键问题：这个系统到底要解决什么？

### 3.1 真实场景（从 Obsidian 推演）

```
场景 1：棉花涨了 3%
  触发：national-stats-mcp 检测到 ICE 棉花变化 >3%
  仿真：传导到纱线 +0.72×3% = +2.16%，传导到面料 +1.4%，传导到 FOB +0.7%
  决策：要不要提前囤纱线？囤多少？
  执行：生成采购建议 → 写入 Obsidian → 通知老板

场景 2：优衣库砍单 30%
  触发：fetch_comtrade_flow 发现日本进口下降 >10%
  仿真：传导到富泉接单 -30%，传导到原料需求 -20%，传导到利润 -15%
  决策：要不要转攻 CHICJOC？保留多少优衣库产能？
  执行：生成 3 个方案 → 老板选 → 写入 Obsidian → 触发下一轮

场景 3：日元贬值 5%
  触发：fetch_fred_observation 检测到 JPY/USD 变化 >1.5%
  仿真：传导到出口收入 -5%，传导到利润 -1.5%
  决策：要不要锁汇？锁多少？
  执行：生成锁汇建议 → 写入 Obsidian
```

### 3.2 融合系统的价值

```
没有融合系统时：
  老板看到"棉花涨了 3%" → 自己判断 → 可能判断错 → 损失

有融合系统时：
  系统自动检测 → 仿真全链影响 → 给出 3 个方案 → 老板选 1 个 → 执行
  
  老板从"自己判断"变成"从 3 个方案中选 1 个"
  决策质量提升 + 响应速度提升 + 知识沉淀
```

## 四、实现路径（渐进式，不是一步到位）

### Phase 0：安全加固（Week 0）✅ 已完成

```
✅ national-stats-mcp 安装
✅ firecrawl 安装
✅ Smithery CLI 安装
✅ 14 个核心 Skills 安装
```

### Phase 1：Execution Layer MVP（Week 1-2）

```
目标：让系统能自动抓数据 + 写报告

1. 配置 national-stats-mcp 到 Claude Desktop
2. 用 firecrawl monitor 监控柯桥指数网页
3. 用 Agent-Reach 监控社交媒体
4. 实现"每日宏观简报"工作流（national-stats-mcp × 4）
5. 验证：老板明天早上 8 点能看到自动生成的简报

工作量：~5 天
技术栈：MCP + firecrawl + Obsidian
```

### Phase 2：Simulation Layer MVP（Week 3-6）

```
目标：让系统能做 what-if 仿真

1. 实现蒙特卡洛模拟器（Python，~500 行）
2. 实现情景分支引擎（"如果 X 涨 10%"）
3. 用已验证的因果系数（0.72/0.96/0.286）
4. 实现"价格异动分析"工作流（自动仿真全链影响）
5. 验证：输入"棉花涨 5%"→ 输出整条链的成本变化

工作量：~15 天
技术栈：Python + numpy/scipy + national-stats-mcp + Obsidian
```

### Phase 3：Policy Layer MVP（Week 7-10）

```
目标：让系统能给出决策建议

1. 实现多目标优化器（成本 vs 质量 vs 交期）
2. 实现风险评分模型（供应链中断概率）
3. 实现策略库（囤料/锁汇/客户分级）
4. 实现"老板对话式探索"工作流
5. 验证：老板问"要不要囤纱线"→ 系统给出 3 个方案

工作量：~15 天
技术栈：Python 优化库 + LLM 推理 + Obsidian
```

### Phase 4：融合闭环（Week 11-14）

```
目标：三个引擎联动

1. 实现主循环（INGEST → UPDATE → SIMULATE → DECIDE → EXECUTE → OBSERVE）
2. 实现反馈学习（执行结果 → 更新系数）
3. 实现跨域传导（棉花→化纤→面料→成衣→零售的全链路模拟）
4. 验证：完整闭环可运行

工作量：~15 天
技术栈：Python + MCP + LLM + Obsidian
```

## 六、核心风险

### 6.1 最大风险：系数精度

```
当前状态：
  ✅ 棉花→纱线 0.72（精确）
  ✅ PTA→POY 0.96（精确）
  ⚠️ 出厂→零售 0.286（品牌溢价干扰）
  ❌ 需求弹性 -0.5（待验证）
  ❌ 汇率传导（未建模）
  ❌ 消费者行为（未建模）

如果系数不准，仿真结果就是垃圾进垃圾出（GIGO）
```

### 6.2 第二风险：数据时效性

```
国统局数据滞后 1 个月
棉花期货实时但需要 API
柯桥指数每周更新但需要爬虫
消费者行为数据几乎没有

仿真需要实时数据，但大部分数据是滞后的
→ 仿真结果有"保质期"
```

### 6.3 第三风险：复杂度爆炸

```
9 环节 × 每环节 3-5 个变量 = 27-45 个状态变量
每条边需要 3 个参数（系数/滞后/置信区间）
蒙特卡洛需要 1000+ 次模拟

总计算量：45 变量 × 9 边 × 1000 次 = 40,500 次计算/次仿真
对 Python 来说不算大，但状态管理复杂
```

## 七、最终判定

### 可行性结论

| 层 | 可行性 | 理由 |
|----|--------|------|
| **Execution（A）** | ✅ **90%** | MCP 已有，Skills 已装，工作流已设计 |
| **Simulation（B）** | ⚠️ **60%** | 因果 DAG 已有，但模拟器需从零编写 |
| **Policy（C）** | ⚠️ **50%** | Agent 架构已有，但优化器需额外开发 |
| **融合闭环** | ⚠️ **55%** | 三层联动需要状态管理和反馈学习 |

### 建议

```
不要一步到位做融合系统。

推荐路径：
  Phase 1（2 周）：Execution MVP → 老板能看到自动生成的简报
  Phase 2（4 周）：Simulation MVP → 老板能问"如果棉花涨 5%"
  Phase 3（4 周）：Policy MVP → 老板能问"要不要囤纱线"
  Phase 4（4 周）：融合闭环 → 系统自动检测→仿真→决策→执行

总工期：~14 周（3.5 个月）
总代码量：~3000 行 Python + ~1000 行 TypeScript
总成本：~¥500（主要是 LLM API 调用）
```

### 与现有方案对比

| 方案 | 工期 | 覆盖度 | 风险 |
|------|------|--------|------|
| 融合系统（一步到位） | 6+ 月 | 100% | 高（复杂度爆炸） |
| 渐进式（Phase 1-4） | 14 周 | 80% | 中（每步可验证） |
| 最小 MVP（仅 Phase 1） | 2 周 | 30% | 低（立即可用） |

---

> **结论**：融合系统在理论上完全可行，但需要渐进式实现。先做 Execution（2 周见效），再做 Simulation（4 周能 what-if），再做 Policy（4 周能决策），最后闭环（4 周）。总计 14 周，~3000 行代码，~¥500 成本。
>
> **最大的杠杆点**：不是写更多代码，而是**用 national-stats-mcp 验证因果系数**——系数准了，整个系统才有意义。
