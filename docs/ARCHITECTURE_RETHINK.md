## 一、退回到原点：这个系统到底为谁解决什么问题？

### 用户画像

```
南通富泉工贸
  100-200 人，4 车间
  对日出口 ODM/OEM
  Excel + 微信群 + 手写单据
  月预算 < ¥900
```

### 真实场景（从 Obsidian 推演）

```
场景 1：老板早上 8 点
  老板想知道：棉花今天多少钱？优衣库那边有消息吗？这个月接了几个单？
  当前做法：打开手机，查 3 个 App，花 30 分钟
  期望做法：打开 Obsidian，1 分钟看完

场景 2：棉花涨了 5%
  老板想知道：对我有什么影响？要不要提前囤纱线？
  当前做法：打电话问采购，采购打电话问纱厂，纱厂说"可能涨"
  期望做法：系统自动算出全链影响，给出 3 个方案

场景 3：优衣库砍单 30%
  老板想知道：损失多少？怎么补？
  当前做法：Excel 算一下，开会讨论
  期望做法：系统算出损失，给出 3 个补救方案
```

### 系统的本质

```
不是 ERP
不是 Agent
不是 Simulation
不是 Decision System

而是：
  "老板的产业链参谋"
  
  老板问一个问题 → 系统从产业链各环节抓数据 → 算出影响 → 给出建议
  
  一句话：用产业链的全局视角，帮老板做更好的决策
```

## 四、正确的架构应该是什么？

### 4.1 从老板的视角设计

```

  09:30  老板问："棉花涨了，对我有什么影响？"
         → 系统自动调用传导引擎，算出 FOB +0.7%
```

## 五、关键设计决策

### 决策 1：MCP 是检测器，不是执行器

```
旧设计：MCP = "抓数据 + 分析 + 写报告"
新设计：MCP = "只抓数据，分析和报告交给传导引擎和 LLM"

原因：
  MCP 擅长：抓数据（HTTP 请求、API 调用）
  MCP 不擅长：因果推理、决策建议
  
  让 MCP 做它擅长的，让传导引擎做推理，让 LLM 做建议
```

### 决策 2：传导引擎是核心，不是附属

```
旧设计：传导引擎是"数学模型的一个组件"
新设计：传导引擎是"整个系统的大脑"

原因：
  没有传导引擎 → 系统只是一个"数据展示器"
  有了传导引擎 → 系统变成"产业链参谋"
  
  传导引擎 = 因果推理 + 非线性传导 + 非对称性
  这是系统的核心价值，不是附属功能
```

### 决策 3：Obsidian 是记忆体，不是文档库

```
旧设计：Obsidian = "存 markdown 文件的地方"
新设计：Obsidian = "产业链的持久化记忆"

原因：
  9 环节 × 56 信息源 × 因果系数 × 系数验证记录
  这些不是"文档"，而是"系统的记忆"
  
  系统每次运行都从 Obsidian 读取记忆
  系统每次运行都向 Obsidian 写入新记忆
  Obsidian = 产业链大脑的海马体
```

### 决策 4：自进化是闭环，不是功能

```
旧设计：自进化 = "一个独立的功能模块"
新设计：自进化 = "系统运行的自然结果"

原因：
  每次老板问问题 → 系统回答 → 老板反馈（有用/没用）
  这个反馈 → 更新系数 → 更新记忆 → 系统变聪明
  
  不需要单独的"自进化模块"
  只需要：执行→反馈→更新 的闭环
```

## 六、简化后的架构（去掉所有不必要的）

```
旧架构（过度设计）：
  25 个平台 × 7 角色 × 10 工作流 × 32 项安全审计 × 5 层自进化
  → 太复杂，没人能维护

新架构（够用就好）：
  
  3 个入口：
    1. 每日简报（自动推送）
    2. 对话探索（老板问答）
    3. 预警通知（事件触发）
  
  1 个核心：
    因果传导引擎（已验证的系数 + 非线性传导）
  
  1 个数据源：
    national-stats-mcp（国统局）+ Obsidian（记忆）
  
  1 个反馈：
    老板的有用/没用反馈 → 更新系数
```
